SemTS
Ontology 1.3.0 GitHub

Everything derived from a time series or known about it, in one graph.

SemTS is an OWL ontology with modular SKOS vocabularies. It links features, predictions, relations and expert knowledge to the intervals, points and dimensions of your data, and records how each piece of knowledge was produced.

Knowledge for AI agents, and from them

An agent that analyses time series needs context: which segments exist, what is already known about them, which assumptions an expert made and which methods worked before. SemTS gives it that context as one queryable graph.

What the agent finds goes back into the same graph as knowledge with its provenance, checked by the SHACL shapes. The next analysis, the next agent and the expert who reviews the result all start from there.

Applications for agents

Data reports in plain language

With everything known about a time series in one graph, a language model can write the report: what was measured, which trends, anomalies and relations were found, what experts know about the process, and how reliable each statement is. Charts of the segments concerned come from the same graph.

Every knowledge item in the graph names the activity that produced it and can carry quality measures, so every sentence of the report can point to the knowledge it is based on. When new knowledge arrives, the report is written again from the current graph.

Applications for reports

Two sources of knowledge, used together

Results computed from the data are only half of what is known about a time series. SemTS keeps the two sources apart, so you always know where a statement came from, and represents them in the same way, so they can be used together.

Derived from the data

Features, trends, anomalies, classifications, forecasts, relations between segments and trained models, each with the method run that produced it and how far it can be trusted.

    Known beforehand, mostly from experts

    Initial assumptions, known facts, operating limits, set points, maintenance events, observations and confirmed labels. They are recorded as scenario or common context knowledge, with the expert annotation or assessment as their source, and are available to analyses from the start.

      Combined, each makes the other more useful

      • An operating limit stated by an expert becomes the threshold of an anomaly detector, and the detector's result points back to the limit it used as input knowledge.
      • A detected anomaly is confirmed or rejected by an expert. The confirmation is knowledge in its own right, with the anomaly as its input.
      • Relations connect a computed result to the assumption it supports or contradicts, so outdated assumptions surface instead of being silently overwritten.
      • Both kinds share the same segments, concepts and provenance model: one query returns everything known about an interval, whatever its source.

            Ontology architecture

            SemTS 1.3.0 has classes and properties in three layers. Select a class or a property to see its definition, axioms and the SHACL rules that apply to it. The complete graph, drawn with WebVOWL, is part of the specification.

            Three ways to scope knowledge

            The property that links a segment to knowledge says how the knowledge applies.

            PropertyMeaningRuleExample

            semts:multiSegmentKnowledgeThe knowledge is only meaningful for the set of segments together.None or at least two segments. A segment relation needs two.Similarity of two heartbeats

            Highlights of version 1.3.0

            • Knowledge relations new
              An abstract KnowledgeRelation that is either directed (source and target) or undirected (two or more participants). The meaning comes from a concept, for example semts-sv:Causes or semts-dv:Correlation.
            • Common context knowledge new
              Knowledge that is attached to segments as context without being scoped to them, linked through commonContextKnowledge.
            • Allen's interval relations
              Thirteen relations between segments, each defined by a property chain over the segment index and the matching OWL-Time relation. The shapes check that an asserted relation is backed by the indexes.
            • Stricter temporal indexes
              A segment has exactly one index: an instant, or an interval with one beginning and one end, both as timestamps or both as numeric positions, with the beginning strictly first.
            • Modular vocabularies
              Data and scenario knowledge are split into stable cores and extension modules. The knowledge generation and quality measure vocabularies are aligned with MLST.

            Standards SemTS builds on

            SemTS imports OWL-Time, DCAT and PROV-O and reuses classes from QUDT, ML-Schema and SKOS instead of redefining them.

            DCAT 3

            Segments are dcat:Datasets with distributions that point to the raw data. Referenced values are dcat:Resources.

            OWL-Time

            Segment indexes are temporal entities. Allen relations between segments follow from the relations between their indexes.

            PROV-O

            Generation entities are activities, inputs and outputs are entities, and used, generated and wasDerivedFrom specialise PROV.

            QUDT

            Units and datatypes of dimensions and values.

            ML-Schema

            Algorithms, hyperparameters, models, implementations and evaluation measures.

            SKOS

            All vocabularies are SKOS concept schemes. Ontology classes point to concepts through three hook properties.

            Vocabularies

            The ontology says what kind of knowledge something is. The vocabularies say what it means. Each knowledge area has a small core vocabulary. Concrete features and domain terms live in modules that build on it.

            The extension modules are examples. The feature catalogue follows one feature library and the manufacturing module covers a handful of domain terms. They show how a core vocabulary is extended and are not meant to be complete. Publish your own catalogue or domain module the same way: new concepts in your own namespace, linked to a core concept with skos:broader.

            Add a domain extension

            The manufacturing module shows the pattern. It stays small on purpose.

            Add a term only when it narrows the meaning. “Machine downtime” earns a place because it restricts the affected entity to a machine. “Production cycle start” was deprecated because the generic Cycle Start already says the same. The manufacturing context belongs in associated knowledge.

            Point to the core with skos:broader. Every extension concept has a broader concept in the core, so queries over the core concept also find the extension terms.

            Import the core, declare the module part of it. The extension imports the core vocabulary and states dct:isPartOf. The browser and the module map on this site are generated from exactly these statements, so a new module appears here without changes to the site.

              Applications

              SemTS is domain-neutral: the examples on this site come from machining, cardiology and building energy. The patterns below are a selection of where the model helps, not a complete list. Each links to the terms and examples it uses.

              Three uses stand out. SemTS structures knowledge for AI agents and from them: agents take their context from the graph and return what they find, with its provenance, for people and other agents to check. It gives language models the material for data reports in plain language, with charts and a source for every statement. And it gives the knowledge that exists before any analysis, the assumptions, facts and observations of domain experts, the same standing as computed results.

              Get started

              Describe a segment, attach knowledge, record where it came from, then validate and query the graph.

              1. Declare the namespaces

                The ontology and each vocabulary module have a permanent w3id IRI.

                PrefixNamespaceModuleVersion

              2. Describe a segment

                A segment needs one temporal index and at least one distribution that points to the data. Add dimensions when you attach data knowledge.

              3. Attach knowledge with a concept

                Pick the class for the kind of knowledge and a concept for its meaning. Data, scenario and method knowledge carry exactly one value.

              4. Record how it was produced

                Every knowledge item names one generation entity. The entity uses inputs and generates outputs that list the knowledge.

              5. Validate with the SHACL shapes

                Load the ontology and the vocabularies next to your data so that class hierarchies and concept types are visible to the validator. The example uses RDFLib and pySHACL. Any SHACL processor that supports SHACL-SPARQL works. The paths are those of the repository.

              6. Query across the hierarchy

                Because feature concepts point to their core family, a query for the family also finds every concrete feature.

                Validation

                The SHACL shapes turn the ontology's intent into checks: cardinalities, value types, disjointness, consistent indexes and complete provenance. They are grouped here by what they protect.

                Run them with any processor for SHACL Core and SHACL-SPARQL. The repository uses pySHACL on RDFLib: python tools/validate.py my-data.ttl loads the shapes, the ontology and all vocabularies, and checks the examples, scenarios and sample data with --repository.

                Changes in 1.3.0

                What is new, what was corrected, and what data written for 1.2.0 needs before it validates.

                New in the model

                • Knowledge relations. KnowledgeRelation with a directed and an undirected subclass relates knowledge items, for example a cause and its effect. The meaning comes from a relation concept.
                • Common context knowledge. Knowledge that holds for a machine, a process or a site rather than for a stretch of data is linked with commonContextKnowledge instead of segmentKnowledge.
                • Modular vocabularies. Each knowledge area has a core vocabulary, with extension modules for concrete features (semts-dfx) and domains (semts-msv). New in this release: knowledge generation (semts-gv, which also holds the concepts for method knowledge) and quality measures (semts-qv).
                • Documentation from the source. This website, the specification and all serialisations are generated from the Turtle files by tools/build.py. WIDOCO is no longer needed.

                Corrections that affect existing data

                • Timestamps carry a time zone. Instants use time:inXSDDateTimeStamp with an xsd:dateTimeStamp value instead of time:inXSDDateTime.
                • QUDT 2 and 3 identifiers. The QUDT schema namespace is http://qudt.org/schema/qudt/. Datatypes come from http://qudt.org/vocab/datatype/, for example FLOAT-DP, BOOLEAN or STRING.
                • Generation and quality concepts come from the SemTS vocabularies. An algorithm is not a knowledge generation concept: the task goes in knowledgeGenerationConcept (for example semts-gv:AnomalyDetection) and the algorithm is linked with mls:implements. Quality measures use semts-qv concepts, which map to MLSO.
                • Every knowledge item names its generation entity, including expert annotations and labels shipped with a dataset.
                • Allen relations are no longer sub-properties of the OWL-Time relations. The property chains still infer them from the segment indexes, and correspondingOwlTimeRelation records the matching OWL-Time relation. isPartOf is transitive but no longer irreflexive, which OWL 2 DL does not allow together.
                • Referenced values are DCAT resources. Point to the file through a dcat:Distribution and type the value as dcat:Dataset when it is a dataset.
